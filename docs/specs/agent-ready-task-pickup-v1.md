# Agent-Ready Task Pickup v1

## Summary

This spec defines the minimum bira changes required for a separate agent to:

1. discover work that is actually actionable,
2. inspect enough context to decide whether to take it,
3. claim it without racing other agents,
4. complete or release it cleanly, and
5. trust that bira is showing the full project state instead of a silent partial view.

v1 stays file-based and local-first. It does not introduce a scheduler, priorities, or remote coordination.

## Problems to Solve

Current bira is a good storage and transport layer, but it does not yet provide workflow semantics for agent pickup:

- tasks can exist with only a title and still look equivalent to fully specified work,
- dependencies are informational only,
- there is no atomic claim operation,
- list/context commands can silently skip unreadable entity files,
- feature and task deletion can leave dangling references,
- agents must reimplement readiness and claim policy outside bira.

## Goals

- Make task readiness explicit and machine-readable.
- Keep grooming permissive: humans may still create incomplete tasks.
- Add an atomic claim flow using the existing project lock.
- Make task handoff information visible in `task show --json` and `task list --json`.
- Fail loud on corrupted or incomplete state instead of silently hiding work.
- Preserve backward compatibility for existing stored projects where practical.

## Non-Goals

- No automatic task prioritization.
- No cross-machine distributed locking beyond the current filesystem lock model.
- No interactive prompts.
- No replacement of `assigned_to` with a richer planning system.

## Data Model Changes

### Agent sessions

Agents are ephemeral. Before claiming any work, an agent starts a bira session. The session ID is the stable identity used for all claim, release, and done operations within that agent's lifetime.

Session files are stored per-project:

```
~/.bira/projects/<project-id>/sessions/<session-id>.json
```

Session schema:

```json
{
  "id": "a1b2c3d4",
  "project_id": "...",
  "label": "search-agent",
  "started_at": "2026-04-07T10:30:00Z"
}
```

Rules:

- `id` is an 8-char hex ID generated by bira on `session start`.
- `label` is an optional human-readable name supplied by the caller. It is used to match `assigned_to` during `task claim`.
- `label` must be unique among active sessions in the project. Reject `session start` with exit code `1` if the label is already in use.
- A session is active until `session end` is called or the project is deleted.
- `BIRA_SESSION` is the environment variable agents use to store their session ID; all commands that accept `--session` fall back to `BIRA_SESSION` if the flag is omitted.

### Stored task fields

Add these fields to the persisted task model:

```json
{
  "claimed_by": "a1b2c3d4",
  "claimed_at": "2026-04-07T10:30:00Z"
}
```

Rules:

- `claimed_by` stores the session ID of the agent that claimed the task.
- `claimed_at` is set when the task is successfully claimed.
- `assigned_to` remains planning metadata (a human-readable name or label). It is not removed or renamed.
- existing task files remain valid; missing `claimed_by` and `claimed_at` mean unclaimed.

### Claim timeout

A claim is considered **stale** when `now - claimed_at > claim_timeout`. Stale claims are treated as unclaimed by both the `ready_for_agent` computation and `task claim`.

- Default timeout: `1440` minutes (24 hours).
- Override per project by adding `claim_timeout_minutes: <N>` to the `.bira` config file.
- Stale claim detection happens at read time; no daemon is required.
- When a claim is stale, the derived field `stale_claim` is set to `true` (see below). The task is considered claimable again — the next `task claim` overwrites the stale `claimed_by` and `claimed_at` without requiring `--force`.

### Derived task fields in JSON output

Do not persist these. Compute them on read and include them in JSON output for `task show`, `task list`, and `context --full`.

```json
{
  "ready_for_agent": true,
  "stale_claim": false,
  "missing_fields": [],
  "blocked_reasons": [],
  "dependency_summary": {
    "total": 2,
    "done": 2,
    "missing": 0,
    "not_done": 0
  }
}
```

Definitions:

- `ready_for_agent` is `true` only when:
  - `status == "todo"`
  - `claimed_by` is empty **or** the claim is stale (see Claim timeout)
  - `description` is non-empty
  - `acceptance_criteria` has at least one entry
  - parent feature exists
  - parent feature is not `done`
  - every `depends_on` task exists and has `status == "done"`
- `stale_claim` is `true` when `claimed_by` is non-empty and the claim has exceeded the project's `claim_timeout_minutes`. A stale claim does not block `ready_for_agent`.
- `missing_fields` contains machine-readable reasons such as:
  - `missing_description`
  - `missing_acceptance_criteria`
  - `missing_feature`
- `blocked_reasons` contains readiness blockers such as:
  - `feature_done`
  - `dependency_missing:<id>`
  - `dependency_not_done:<id>`
  - `already_claimed`
  - `status_not_todo`

`task show --json` must also include resolved dependency entries:

```json
{
  "dependencies": [
    { "id": "aaaabbbb", "exists": true, "status": "done", "title": "Write parser tests" }
  ]
}
```

If a dependency file is missing, return:

```json
{ "id": "aaaabbbb", "exists": false }
```

## Command Changes

### `bira task list`

Add filters:

- `--ready`
- `--assigned <name>`
- `--unassigned`
- `--claimed-by <name>`
- `--unclaimed`

Behavior:

- filters compose with existing `--feature` and `--status`
- `--ready` returns only tasks where `ready_for_agent == true`
- `--assigned` filters on `assigned_to`
- `--claimed-by` filters on `claimed_by`
- `--unassigned` and `--unclaimed` match empty values only
- human-readable output adds `READY` and `CLAIMED BY` columns
- JSON output includes the derived readiness fields

Ordering:

- sort tasks deterministically by `created_at ASC`, then `id ASC`
- sort features deterministically by `is_backlog DESC` (backlog first), then `created_at ASC`, then `id ASC`
- apply the same ordering in `task list --json`, `feature list --json`, and `feature/task summaries` returned from `context --full --json`

### `bira task show`

JSON output must include:

- stored task fields,
- resolved parent feature summary:
  - `feature: { "id": "...", "name": "...", "status": "..." }`
- readiness fields,
- resolved dependencies array.

Human-readable output adds:

- `Claimed by` — displays `<label> (<session-id>)` if the session file exists, otherwise `<session-id> (session not found)`
- `Claimed at`
- `Stale claim` — shown only when `stale_claim == true`
- `Ready for agent`
- `Missing fields`
- `Blocked reasons`

### `bira task claim`

Add a new command:

```bash
bira task claim <id> --session <session-id> [--force]
```

`--session` defaults to `$BIRA_SESSION` if the env var is set.

Behavior:

- acquires the project lock before load-check-update-save
- fails with exit code `1` unless all claim preconditions pass
- preconditions without `--force`:
  - task exists
  - session exists in the project
  - `ready_for_agent == true` (stale claims pass this check)
  - `claimed_by` is empty **or** the existing claim is stale
  - `assigned_to` is empty, or equals the session's `label`, or equals the session ID
- on success:
  - set `claimed_by = <session-id>`
  - set `claimed_at = now`
  - set `status = "in-progress"`
  - update `updated_at`
- `--force` bypasses the `assigned_to` check only
- `--force` does not bypass `status_not_todo`, missing description, missing criteria, missing feature, dependency failures, or an active non-stale claim
- to claim a `blocked` task whose blockers are resolved, first run `task update <id> --status todo` (which requires the task to be unclaimed), then claim it
- claim conflicts (already claimed with active claim, precondition failures) use exit code `1`, not `2`, because the task exists but the workflow rule is violated

Human-readable output:

- on success: `Claimed task "<title>" (<id>) by <label> (<session-id>)`

JSON output returns the updated task including readiness metadata after the change.

### `bira task release`

Add a new command:

```bash
bira task release <id> --session <session-id> [--status todo|blocked] [--note <message>] [--force]
```

`--session` defaults to `$BIRA_SESSION` if the env var is set.

Behavior:

- default release status is `todo`
- only the session that holds `claimed_by` may release unless `--force` is supplied
- on success:
  - clear `claimed_by`
  - clear `claimed_at`
  - set `status` to the requested status
  - append a note if `--note` is provided
  - update `updated_at`
- `--status done` is invalid; use `task done --session <id>` to complete a claimed task
- `--status` only accepts `todo` (default) or `blocked`; this keeps `task done` as the single completion path, ensuring consistent done-transition behavior across all workflows

Human-readable output:

- on success: `Released task "<title>" (<id>) by <label> (<session-id>) [status: <status>]`

### `bira task done`

Change existing behavior:

- if the task is claimed, `task done` clears `claimed_by` and `claimed_at`
- if `--session <id>` is supplied and the task is claimed by a different session, fail with exit code `1`
- if `--session <id>` is supplied and the task is unclaimed, succeed normally (no claim conflict)

New form:

```bash
bira task done <id> [--session <session-id>]
```

`--session` defaults to `$BIRA_SESSION` if the env var is set.

If `--session` is omitted and `BIRA_SESSION` is not set, preserve current permissive behavior (no claim check).

### `bira task update` (changed behavior)

Add a claim-protection rule:

- if the task has a non-empty `claimed_by`, reject `--status` changes with exit code `1`
- error message: `task <id> is claimed by session <session-id>; use "task release" or "task done" instead`
- non-status field updates (description, tags, criteria, etc.) remain allowed on claimed tasks

### `bira session`

Add a new command group for managing agent sessions:

```bash
bira session start [--label <name>]
bira session list
bira session show <session-id>
bira session end <session-id> [--release-status todo|blocked]
```

#### `bira session start`

- generates a new 8-char hex session ID
- stores the session file under `~/.bira/projects/<id>/sessions/<session-id>.json`
- `--label` is optional; if supplied, it must be unique among active sessions in the project (exit code `1` on collision)
- JSON output:

  ```json
  { "id": "a1b2c3d4", "label": "search-agent", "started_at": "2026-04-07T10:30:00Z" }
  ```

- Human-readable: `Session started: a1b2c3d4 (search-agent)`
- The caller is expected to store the session ID in `BIRA_SESSION` for subsequent commands

#### `bira session list`

- lists all active sessions for the current project
- JSON output includes `id`, `label`, `started_at`, and `claimed_task_count` (tasks currently claimed by this session)
- Human-readable: table with `SESSION`, `LABEL`, `STARTED`, `CLAIMED` columns

#### `bira session show <session-id>`

- shows session details and all tasks currently claimed by this session
- JSON output includes the session fields plus a `claimed_tasks` array (same shape as `task list --json` entries, with readiness fields)

#### `bira session end <session-id>`

- acquires the project lock
- releases all tasks currently claimed by this session:
  - clears `claimed_by` and `claimed_at` on each task
  - sets each task's `status` to `--release-status` (default: `todo`)
  - appends an auto-generated note: `Released by session end (<session-id>)`
- deletes the session file
- `--release-status` accepts `todo` (default) or `blocked`
- JSON output: `{ "released_tasks": ["<id>", ...] }`
- Human-readable: `Session a1b2c3d4 ended. Released N task(s).`

### `bira context --full`

Keep the current top-level fields and per-feature `tasks` status counts.

Add:

```json
{
  "ready_task_count": 4,
  "claimed_task_count": 2,
  "invalid_task_count": 3,
  "active_session_count": 2,
  "features": [
    {
      "id": "abcd1234",
      "name": "auth",
      "status": "in-progress",
      "is_backlog": false,
      "tasks": { "todo": 3, "in-progress": 2, "done": 1 },
      "agent": {
        "ready": 2,
        "claimed": 1,
        "invalid": 1
      }
    }
  ]
}
```

Definitions:

- `ready_task_count`: total tasks where `ready_for_agent == true`
- `claimed_task_count`: total tasks with non-empty `claimed_by`, `status == "in-progress"`, and a non-stale claim
- `invalid_task_count`: total tasks where `status == "todo"` and `claimed_by` is empty, but `ready_for_agent == false` due to missing fields or referential failures (missing description, missing acceptance criteria, missing feature, broken dependencies). Tasks that are `in-progress`, `blocked`, `done`, or claimed are excluded from this count.
- `active_session_count`: number of session files currently in the project's sessions directory

## Integrity and Validation Rules

### Read commands must fail loud

Change `loadAllTasks` and `loadAllFeatures` behavior:

- if any entity file cannot be read or parsed, abort the command with exit code `1`
- stderr must identify the entity file path and parse failure
- do not silently skip unreadable entities

Commands affected:

- `feature list`
- `task list`
- `context`
- any helper flow that currently scans all entities to compute results

### Dependency validation on write

On `task add` and `task update`:

- every `depends_on` ID must exist in the same project
- self-dependency is invalid
- duplicate dependency IDs are invalid
- circular dependencies are invalid: walk the full dependency chain from the target task and reject if the current task ID appears (A→B→C→A)

Return exit code `2` for missing dependency tasks and exit code `1` for malformed dependency sets (self-dep, duplicates, or cycles).

### Feature deletion

Change `feature delete <id>` behavior:

- if any tasks still reference the feature, fail with exit code `1`
- add `--move-tasks-to <feature-id>` to support explicit migration during delete
- `--move-tasks-to` may target the backlog feature or another non-deleted, non-done feature in the same project
- migration happens under the same project lock before deleting the feature file

### Task deletion

Change `task delete <id>` behavior:

- if any non-done task depends on the target task, fail with exit code `1`
- error message must list the dependent task IDs

## Output and Error Semantics

- Keep the existing rule that JSON data is written to stdout and errors to stderr.
- Keep existing exit codes:
  - `0` success
  - `1` general validation or workflow error
  - `2` entity not found
- Claim/release conflicts use exit code `1`, not `2`.
- Add tests for all new command and validation branches.

## Backward Compatibility

- Existing project and task JSON files remain readable without migration.
- Existing commands remain valid unless they now violate a new integrity rule.
- Existing automation using `task list --json` continues to work because new JSON fields are additive.
- `context --full --json` remains backward compatible by preserving existing fields and appending new counters.

## Example Agent Workflow

```bash
# Start a session and export the ID
export BIRA_SESSION=$(bira session start --label "search-agent" --json | jq -r '.id')

# Discover actionable work
bira task list --ready --unclaimed --json

# Inspect one task deeply
bira task show 1a2b3c4d --json

# Atomically take ownership (--session read from BIRA_SESSION)
bira task claim 1a2b3c4d --json

# Record a blocker and release the task
bira task release 1a2b3c4d --status blocked --note "Waiting on API schema" --json

# Reclaim later and complete it
bira task claim 1a2b3c4d --json
bira task done 1a2b3c4d --json

# Clean up: end session and release any remaining claimed tasks
bira session end $BIRA_SESSION
```

## Implementation Notes

- compute readiness in a shared helper so `task list`, `task show`, `task claim`, and `context` use identical logic
- claim timeout check is part of readiness computation; pass the project's `claim_timeout_minutes` (from `.bira` config, default 1440) into the shared helper
- keep write paths lock-protected using the current per-project advisory lock
- add deterministic sorting before rendering output
- do not reuse the silent-skip load helpers; replace them with load helpers that return aggregated errors
- `task list --ready` does not hold the lock, so a task visible as ready may be claimed by another agent before `task claim` runs; this is expected — `task claim` will fail cleanly and the agent should retry with the next available task
- `session end` must run under the project lock so it atomically releases all claimed tasks before deleting the session file

## Acceptance Tests

Add command-layer tests for:

- `task show --json` returns readiness fields and resolved dependencies
- `task list --ready --json` returns only fully specified unclaimed todo tasks with all dependencies done
- `task claim` sets `claimed_by` (session ID), `claimed_at`, and `status=in-progress`
- `task claim` fails when `assigned_to` does not match session label or ID without `--force`
- `task claim` fails when dependencies are incomplete
- `task claim` succeeds over a stale claim without `--force`
- `task release` clears claim metadata and appends a note when requested
- `task done --session` fails for a different session and clears claim metadata for the owning session
- `task done --session` succeeds on an unclaimed task
- `task update --status` fails on a claimed task with exit code `1`
- `task add` and `task update` fail on circular dependencies with exit code `1`
- `task add` and `task update` fail on self-dependencies with exit code `1`
- `feature delete` fails when child tasks exist unless `--move-tasks-to` is supplied
- `feature delete --move-tasks-to` fails when target feature is `done`
- `task delete` fails when active dependents exist
- `context --full --json` includes ready, claimed, invalid, and active session counters
- malformed task or feature JSON causes `task list` or `context` to fail instead of silently omitting data
- `session start --label` fails when label already in use
- `session end` releases all claimed tasks and deletes the session file
- `session end` sets released tasks to the requested `--release-status`
- a task with a claim older than `claim_timeout_minutes` has `stale_claim: true` and `ready_for_agent: true`

## Definition of Done

This spec is complete when bira can be used by an external agent with this loop:

1. list ready work,
2. inspect one task,
3. claim it atomically,
4. trust that dependencies and references are valid,
5. release or finish it without leaving stale ownership,
6. and detect corrupted project state as an error instead of a partial success.
